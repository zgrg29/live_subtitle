## 2026-10-21 · 从零到能用

一天里把一个空仓库做成了能跑通全链路的绿色版 exe，走完了三个阶段。

### M0 骨架（上午）

**做了什么**：音频采集 → VAD 切句 → 识别接口 → 翻译接口 → WebSocket → OBS 字幕页，
加逐句延迟统计、会话 JSONL、单文件 TOML 配置、样式系统、预排版模式、CLI、单元测试。

**验证**：合成音频自测产出 4 句，"说完→上屏" 420ms（只有切句等待，识别/翻译都是 0ms）。

**当时的判断**：延迟大头是"等静音"，不是模型。这个判断后来被证实了。

### M1 真实日语识别（中午）

**选型**：`csukuangfj/reazonspeech-k2-v2`（ReazonSpeech k2 v2 的 ONNX 转换，Apache-2.0，int8 153MB）。

**实测**（5 条测试音频，共 50.5 秒）：

| 线程 | RTF |
|---|---|
| 1 | 0.159 |
| **2** | **0.113** |
| 3 | 0.169 |
| 4 | 0.204 |

线程数超过 2 反而变慢（N97 只有 4 个能效核，超订）。

**质量**：平均 CER 4.5%，错误基本是数字写法差异（`１８歳` → `十八歳`）。

**顺手修的 bug**：单句到 8 秒上限时硬切会把词劈开（`高額であ|課題と…`），改成在最近的低能量点切，
剩余音频留给下一句。

### M2 真实翻译（下午，返工两次）

**第一版 M2M100-418M（MIT，CT2 int8）**：300–800ms/句，但质量不可接受——
`こんばんは` → "晚餐好"、`今日のごはんは何ですか？` 干脆不翻。

**第二版 Qwen LLM（llama.cpp）**：试了 0.5B 和 1.5B。

| 模型 | 质量 | 单句延迟 |
|---|---|---|
| Qwen2.5-0.5B | 不稳定（漏翻、重复） | 1.2–1.8s |
| Qwen2.5-1.5B | 好 | **1.7s**（最慢 2.9s） |

根因：这台机器是 **Intel N97**（4 个能效核），1.5B 光预填充就要 1 秒。LLM 路线在实时字幕上不可行。

**第三版 opus-mt-ja-zh 75M + ONNX int8（当前）**：

- 质量接近 1.5B（`高兴认识你`、`我得去一下厕所了`、`这个游戏,真是很难玩,不是吗?`）；
- 单句 **45–103ms**，模型 229MB。

中间踩了两个坑：

1. **CTranslate2 转这个 Marian 会坏**：输出退化成单字（"同""。"），而同一模型用 transformers 跑完全正常。
   是转换工具的 EOS/decoder_start 标记错位，不是模型问题。
2. **optimum 导出的 ONNX 没有 KV cache**：每步重算整句，529ms；补上手写的 cache 循环后 234ms，
   再量化到 int8 后 **79ms**。

## 2026-10-21（续）· M2.3 断句合并

### 问题不是"切得碎"，是"碎句让识别变差"

先用真实链路跑 `1.wav`（NHK 播音，逗号处有停顿）：

```
気象庁は                         → 气象局
雪や路面の凍結による交通への影響    → 雪或路面冻结对交通的影响
暴風雪や高波に警戒するとともに       → 警惕暴风雪和高浪,
気崩れや屋根からの落雪にも…        → 我们也呼吁大家注意…
```

最后一句的 `気崩れ` 是碎片化的代价（原词 `雪崩`）。把整段合并后重新识别，
ASR 恢复成 `雪崩`。所以这不是"显示层"的问题，是切句策略的问题。

### 做了什么

- `text/ja.py`：句尾规则（助词/接续词/て形 → 没说完；`です・ます・た・ね・か`、辞书形 → 说完了；
  短句/名词结尾 → 先当没说完），以及语气词清理；
- `composer.py`：声学 320ms 收句后，没说完就暂缓最多 800ms；后续来了合并、只翻一次；
  等不到就到点出；最多 2 次合并 / 12s；等待按音频时间轴算；
- 合并识别：上一段 < 2.5s 重识别（补上下文），长片段拼文本（省一次长 ASR）；
- `config.toml` 新增 `[segment]`；`metrics`/`selftest`/`/api/metrics` 增加合并统计；
- `tools/eval_pipeline.py`：一条命令复现"几行 / 合并几次 / CER / 延迟"。

### 数字（5 条测试音频，共 50.5s）

| 指标 | 改前（420ms 硬切） | 改后（320ms + 合并） |
|---|---|---|
| 最终字幕行数 | 12 | **8** |
| 整句 CER | 11.1% | **4.6%** |
| 1.wav | 4 行 / CER 3.2% | **2 行 / CER 0.0%** |
| 2.wav | 2 行 / CER 27.6% | **1 行 / CER 0.0%** |

> 拆开量：只合并（不补静音）是 **6.1%**，只补段首静音是 **9.1%**，两项一起才是 **4.6%**。
> 段首静音（`asr.lead_pad_ms`）修的是离线 transducer 在几乎没有前导静音时吞掉第一个短词
> （`はやく…` → `…`），但它在"碎句"上会帮倒忙（2.wav 单独补静音反而 31.0%），
> 真正发挥作用是在合并后的完整音频上。

延迟：短句 p50 仍在 0.8–1.2s；长句（6–14s）p50 1.2–1.9s，因为合并会多识别一次短片段。
`selftest` 里新增 `[合并 N 段]` 标记和"暂缓/超时/丢弃语气词"统计。

### 踩的坑

1. `max_hold_ms` 一开始设 5s，比"续段 4.8s"还短，长句在快合并时被提前拆开。
   护栏必须大于单段上限（8s），改到 12s，正常不触发。
2. `Segmenter._seg_start_ms` 一开始取了缓冲起点，但缓冲含 pre-roll（最多 360ms），
   导致合并窗口算错。必须用 `_pos_ms - 连续说话时长`。
3. 语气词片段不能直接 `return`：正暂缓着「このゲームは」时来一个「えーと」，
   会把合并链打断。现在把音频并进去（`_absorb`），继续等。
4. 合并后重识别不是永远更好：`1.wav` 的长片段重识别曾把 `暴風雪` 前面幻觉出 `気象台は`。
   所以只对短片段重识别，长片段拼文本。
5. 段首短词被吞不是切句问题，是离线 transducer 需要前导静音：`はやく…` 整句开头丢失，
   在 ASR 输入前补 200ms 静音就恢复（`asr.lead_pad_ms`）。

### 重新打包（0.2.1）

- PyInstaller 6.22.3，约 4 分钟，`dist\LiveSub` 602MB；
- 实测 exe：`LiveSub.exe --wav 3.wav --port 8772` → `count=1`、`merged_segments=1`、
  `audio_ms=5410`、`end_to_line=1132ms`、`/overlay` 200；
- 说明 `composer` / `text` / `lead_pad_ms` / `[segment]` 配置都已经进包。

### 留下的

- 真人麦克风前的断句 A/B（现在只有播音腔 WAV）；
- 长名词句、动词中顿（`舞い`）仍会漏判，下一步考虑标点模型或更强的句尾分类；
- 合并错了（两句硬连）比切碎难看，目前靠 800ms 窗口 + 2 次上限控制风险。

## 2026-10-21（交接）· 下一个对话：名词词典

**现象**：食物名/专有名词经常不对，例如 `のり弁当`（海苔便当）、`唐揚げ`、`卵焼き`、`味噌汁`、
`おにぎり`，以及游戏名、角色名、直播用语。

**先分清错在哪一层**（下一个对话第一件事）：

1. 看字幕页的日语原文（`overlay.bilingual = true`）；
2. 如果 `ja` 就错了（`のり弁当` → `のりべん` / `乗り弁当`）→ **ASR 层**：
   同音/近音替换、热词，严重时换更大的识别模型；
3. 如果 `ja` 对、`zh` 错/不译 → **MT 层**：翻译后术语表最便宜，几乎零延迟；
4. 如果两段都对、组合后语义错 → 翻译模型能力问题，词典救不了，考虑换模型 A/B。

**计划**（详见 ROADMAP M2.2）：

- `[glossary]`：翻译后替换 + 不翻译名单（角色名/游戏名）；
- `[asr.replace]`：只针对真实错例做定向修正，不猜；
- 内置直播用语 + 常见食物默认表，用户可覆盖；
- 先用 20 条真实错例验收，别凭感觉加词。

**判断**：食物名大概率是 ASR 的发音/词表问题，单纯加翻译词典只能救"日语听对了但中文没翻对"
的那部分；如果 `ja` 本身错了，优先试 ASR 侧替换或换模型。

## 2026-10-21（续）· M2.2 术语表：先做裁判，再补词

### 决策前提（这次先谈清楚了）

目标是**低延迟、低消耗优先，质量第二**，而且**验收基线是这台 N97 迷你机**——不是"主播的
游戏 PC 上应该更快"。所以任何 ≥1B 的模型（Hy-MT2-1.8B / TranslateGemma 4B）直接出局，
不做分档、不做"有显卡就更准"的 B 档。剩下的路只有一条：**模型不换，用文本补**。

### 先建裁判：60 句评测集

`eval/mt_eval.jsonl`，5 类各 12 句：寒暄 / 直播 / 游戏 / 名词 / 长句，每句带 `ref`
（参考译文）、`note`（考点），部分句子带 `alt`（同样正确的其他译法，评分取最高）。
`tools/eval_mt.py` 一次跑完，输出 Markdown + JSON，`--no-glossary` 用来跑裸模型做 A/B。

**基线把文档里的说法证伪了**：

| 指标 | 裸模型（60 句） |
|---|---|
| 字符 bigram F1 | **0.354** |
| F1 < 0.2（明显错） | **24 / 60** |
| 延迟 | p50 71ms / max 194ms |

README 之前写的"日常口语可读"是拿 4 个挑过的例子得出的。真实分布是：约 40% 明显错，
只有 4 句算好。**失败几乎全在词汇层**，不是语法层：

| 类型 | 例子 |
|---|---|
| 片假名外来语音译/幻觉 | `マイク`→"迈克"、`スパチャ`→"spacha"、`アーカイブ`→"archibe"、`ラーメン`→"拉玛"、`タピオカミルクティー`→"Lapping Rucki" |
| 定型寒暄 | `こんばんは`→"晚安"、`おつかれさまでした`→**"我抓住了你"**、`チャンネル登録`→"注册您的频道" |
| 多义词 | `配信`→发送 / 发货 / 传送 |
| 语义反转 | `めちゃくちゃうまい`→"不爽" |
| 解码崩溃 | `フレームレート`→"Flame"×7（502ms） |

### 三种注入方式，实测后再选

拿 10 个句子分别试「译前注入中文」「哨兵 QXZ」「译后替换」：

| 方式 | 例子（`マイクの音量、大丈夫ですか？`） | 结论 |
|---|---|---|
| 译前注入中文 | "麦克风的声音,你好吗?" | 词保住了，但**整句被改写**（原句的"大丈夫"丢了） |
| 哨兵 `QXZ` | "QXZ音频,你还好吗?" | 10/10 原样保留，还原最稳；但模型不知道词义，周围动词会怪 |
| 译后替换 | base"迈克的音量好吗?" → "麦克风的音量好吗?" | 对"句子对、只有词错"最干净 |

所以按词性分模式，而不是一刀切：`pre` 用于片假名专名/食物名（`スパチャ`→"超级留言" 几乎完美），
`post` 用于 `配信` 这种句子结构本来正确的词。

### 结果（同一套 ref，跑两遍）

| 指标 | 裸模型 | + 术语表 | 变化 |
|---|---|---|---|
| F1 均值 | 0.354 | **0.605** | +71% 相对 |
| F1 < 0.2 | 24 / 60 | **5 / 60** | −19 句 |
| 延迟 p50 | 71ms | 75ms | ~0（12 句走整句表，0ms） |
| 延迟 max | 194ms | 180ms | 解码护栏省出来的 |

分类：寒暄 0.365→**0.810**、直播 0.329→0.535、游戏 0.359→0.557、名词 0.211→**0.489**、长句 0.506→0.633。

### 补测：把标点去掉，分数掉回 0.456

上面的 0.605 是在**带标点的书写体**上测的，而线上喂给翻译的是 ASR 输出——流式 transducer
不吐标点（`ヤンバルクイナとの出会いは十八歳の時だった` 这种）。把同一批句子去掉标点重跑：

| 输入 | 裸模型 | + 术语表 |
|---|---|---|
| 书写体 | 0.354（错 24） | **0.605**（错 5） |
| 无标点 | 0.273（错 28） | **0.456**（错 13） |

掉下来的原因不是词，是**句法线索**：`この敵前より強くなってない`（没有 `？`）被读成陈述句，
`アーカイブは後で上げます`（没有 `、`）被切成奇怪的短语。同时暴露了 `post` 模式的脆弱：
错误写法写的是 `archibe`，模型吐 `archib`；写的是"老大"，模型这次给"老板"——猜不中就失效。
**结论：`pre` 模式更稳（命中即生效），`post` 只在"错误写法高度稳定"时才用。**

所以真实基线应该按 **0.456 / 错 13 句** 记；下一步优先试**译前补标点**（把 ASR 输出补上
「、」「？」再送翻译），这是零延迟且可能拿回一半差距的动作。

词典规模只有 **48 条固定表达 + 28 条术语**，全部是"实测翻错才加"。

### 踩的坑

1. **`发送` 与 `发送邮件` 的替换顺序**：先替换短的会留下"开始直播邮件了"。错误写法必须按长度倒序。
2. **空格让重复折叠失效**：`帧数 帧数 帧数` 的正则抓不到（最后一个没有尾随空格）。改成"按空白切开，
   全一样就折叠"。
3. **`マイク` 用 pre 反而更差**：模型把"麦克风的音量"改写成"麦克风的声音，你好吗"。改 post 就对了。
   同一个词在不同句子里，pre/post 的胜负会反转，**只能实测，不能推理**。
4. **`のり弁当` 用 pre 更差**：注入"便当"→"我做了空乘"，注入"海苔便当"→"我做了海苔"。
   食物名这块仍然弱，保留 pre 但记录在案。
5. **解码护栏没拦住"Flame"**：token 不是整词，`run>=5` 永远不触发。补了一条"整段 token 序列自重复"检测
   （`tokens[-6:] == tokens[-12:-6] == tokens[-18:-12]`），502ms → 180ms。

### VTuber 语料：真实水平是 0.244，不是 0.605

不能录真人麦克风（ASR 和 MT 是两条轴），但"我写的书面语"也不是真实分布。
于是另写了一份 **40 句 VTuber 语域**的 holdout（`eval/holdout_vtuber.jsonl`）：
雑談 / ゲーム実況 / スパチャ読み / コラボ / 歌枠 / 謝罪 / 告知 / ツッコミ，
全是タメ口、ネットスラング、口癖。**写的时候不看词典，也不拿它调参**。

| 语料 | 裸模型 | + 补标点 + 术语表 |
|---|---|---|
| 60 句书写体 | 0.354（错 24） | **0.605**（错 5） |
| 60 句无标点 | 0.273（错 28） | **0.504**（错 10） |
| **40 句 VTuber** | 0.179（错 25） | **0.244**（错 19） |

掉得非常狠，而且不是评分苛刻——逐句看，错的是真错：

| 原文 | 输出 | 错在哪 |
|---|---|---|
| うわ、今の絶対当たってたでしょ！ | 是的，你肯定已经赢了！ | 主语/时态全错 |
| 今のプレイ、クリップしてもらえると嬉しいです | 我很高兴能够在这里，点击 | 外来语不认识 |
| 今日は〇〇さんとコラボです | 今天，我和百度一起 | 专名幻觉 |
| 草、そんなコメント来ると思わなかった | King，我不认为我会评论这个评论 | ネットスラング完全不认识 |
| はいはい、わかった、もういいよ | 是的，好的。 | 口语语气全丢 |

结论：**之前 0.605 是"我出题、我加词"造成的乐观偏差**。真实语域下，75M 的可用性大约到
"一半句子能看懂、另一半要猜"。

### 词典差点把好句子改坏：`リンク`

VTuber 语料里出现 `概要欄にリンク貼ってます`，输出是"林克在 second 栏中"——
因为我把 `リンク` 按"塞尔达里的林克"加进了 post 表（`链接 → 林克`），
而日文里 `リンク` 更常见的意思是**超链接**。已删除该词条。

教训：**同形异义的词不能进 post 表**。判断标准不是"模型会不会翻错"，而是
"这个词在别的语境里会不会被我不小心改掉"。`マイク` 的 `Mike` 也是同类问题
（错误写法只写了"迈克"，模型吐 `Mike` 就没兜住）——post 表必须把已知错法列全。

### 补标点：只补句末就够

| 处理 | F1 | 明显错 |
|---|---|---|
| 无标点 | 0.456 | 13 |
| 只补逗号 | 0.485 | 13 |
| 只补句末 | **0.504** | **10** |
| 逗号 + 句末 | 0.503 | 10 |

逗号没有净收益（改好 6 句、改坏 5 句），所以默认只补句末（`mt.punctuate`），
成本 0ms，书写体输入上是 no-op。

### 留下的（更新）

- 剩下 5 句（书写体）/ 19 句（VTuber）明显错，主力是**口语语法**（でしょ、じゃん、〜ちゃった、
  〜てくれて）和**ネットスラング**（草、エグい、詰み），这是 75M 的天花板；
- 下一步要一份**新的口语 dev 集**用来调词（不能再拿这份 holdout 调，否则它就不是 holdout 了）；
- 词典过拟合的风险已经量化：0.605 → 0.244，差 0.36。

## 2026-10-21（续）· 口语 dev 集：词典的边际收益到顶了

### 做法

按用户的要求，语域锁定在**日本 VTuber 的三块主要内容：雑談 / 歌枠 / ゲーム**。
新写 30 句 `eval/dev_vtuber.jsonl` 当**调参集**；`holdout_vtuber.jsonl` 冻结，只在汇报时跑。

### 数字

| 语料 | 调词前 | 调词后 | 明显错 |
|---|---|---|---|
| 30 句 dev（照着它调） | 0.235 | **0.275** | 16 → 11 |
| 40 句 holdout（只汇报） | 0.244 | **0.263** | 19 → 17 |
| 60 句书写体（回归检查） | 0.603 | 0.603 | 5 → 5 |

dev 涨 0.04，holdout 涨 0.019——**这就是"名词类词条"的全部剩余价值**。
（holdout 那句 +0.019 还要打折：加词前我已经看过它的错误，算是软污染。）

### 有效的词

`歌枠→唱歌回`、`リクエスト→点歌`、`凸待ち→连麦`、`概要欄→简介`、`メンバーシップ→会员`、
`ダメージ→伤害`、`コンビニ→便利店`、`明後日→后天`、`詰み→死局`（"我死定了"，语义对）。

### 加错的词（又踩一次）

| 词 | pre 注入后 | 结论 |
|---|---|---|
| `クリア` | "么么么" | 撤掉，改 post（`干净→通关`） |
| `セーブ` | "留在这里，留住，留住" | 撤掉，改 post（`保持安静/记住→存档`） |

又一次印证：**同一个词 pre 还是 post，只能实测**。

### 抓到一个通用 bug：重复检测只认"整句周期"

`声出てる？マイクの音量、大丈夫かな。` 解码成 `麦克风 comming 麦克风 comming 麦克风 麦克风 麦克风`
——开头在打转、尾巴还拖着。原来的折叠要求**整句**周期性，所以抓不到。
改成"只看前缀周期"：`words[period:2*period] == words[:period]` 就整句只留一个周期。

顺带把 post 替换改成**忽略大小写**（模型有时吐 `Mike`、有时吐 `mike`，原来只匹配小写）。

### 剩下的 18 句错在哪（全部是语法，不是词）

| 例子 | 输出 | 缺什么 |
|---|---|---|
| え、もうそんな時間？まだ何もしてないのに | 现在，时间到了吗？我什么也没有做 | 时制 + のに 的反预期 |
| ちょっとコンビニ行ってくるね | 我得去便利商店，等等 | てくる 的方向感 |
| ここでセーブしとくね | 在这里，存档，存档 | しとく（=しておく）的缩约 |
| ちょっとキー下げてもいい？ | 我可以放下一点钥匙吗 | キー下げ 的动词化 |
| 今日はちょっとだけしかできないんだけど | 今天，我只能做一点点… | しか〜ない 的限定 |
| みんなのおかげで、ここまで来られたよ | 感谢你们，我来到了这里 | おかげで + 可能形 |
| 今の攻撃当たってないんだけど | 我们没有受到任何攻击 | 否定 + 被动/主动 |

**结论：词典这条线基本挖到底了。** 再多加名词也不会动 0.27。
要往下走只有三条路，都是架构级的（见 HANDOFF 下一步）。

### 顺手试掉的一条错路：口语规范化

假设：Marian 的语料以书面语为主，`しとく / ちゃった / てる / んだ` 这些缩约它没见过几次，
译前把它们改回 `しておく / てしまった / ている / のだ`（0ms 的字符串替换）也许能白捡质量。

**实测：没用。**

| 语料 | 原样 | 规范化后 |
|---|---|---|
| 30 句 dev | 0.275 | 0.272 |
| 40 句 holdout | 0.263 | 0.264 |

误差范围内。说明模型的错不在形态层——它认得出 `しとく`，错的是**语义和句法**：
`おかげで` 的因果、`しか〜ない` 的限定、`びっくりした` 的时制。规范化救不了这些。
这条假设可以关掉了，省得以后有人再想一遍。

## 2026-10-21（续）· 设置页 + 高频日常口语

### 用户反馈：`こんばんは` 还是"晚安"

查下来不是一处，是**一类**：整句表只认完全一致，所以

- `こんばんはー`（带拖音）匹配不上 → 落回模型 → "晚安"；

## 2026-10-22 · 主播反馈的 5 项 UX（0.5.0）

### 反馈原话（转述）

1. 说完一句以后如果沉默了，字幕会一直挂在屏幕上，希望过一会儿自动消失（多久合适？）；
2. 设置里要能选麦克风（电脑上有多个）；
3. 说话小声时识别不到，可能是阈值太高；希望能自己调音量/灵敏度，最好有 OBS 那种实时电平；
4. 打开软件时就应该把设置页在浏览器里打开，不要让用户自己敲地址；
5. 想要一个默认关闭的录音功能：录音频 + 识别到的日语 + 中文翻译，拿回来做持续改进。

### 先想清楚「多久」

字幕停留时间不是越短越好：停留太短，观众读到一半就没了；太长，沉默时屏幕一直挂着。
定的是 **5 秒基准 + 按字数延长**：

- 新句子出现时重置计时（连续说话时永远不会触发）；
- 估算阅读速度约 6–8 字/秒，`max(5000, 1500 + 字数×130)`，上限 15 秒；
- `0` 表示永不自动清屏，给「想一直留最后一句」的人；
- `?preview=1` 预排版页不清屏，否则调字体时文字会自己消失。

### 麦克风：同名设备是个坑

设置页第一版只打算保存设备名，实测发现这台机器有 **3 个同名的
`麦克风 (USBAudio1.0)`**，PortAudio 按名字取第一个，用户选第二个也会打开第一个。
所以配置里同时保存 `device`（名字，兼容手写）和 `device_index`（精确选择）：

- 切换时先关旧流再开新流（Windows 上很多麦克风是独占的，同时开会失败）；
- 新设备打不开就用旧设备重建，**配置不落盘**，直播不中断；
- 重启后索引变了（换 USB 口）就按名字找，`resolve_input_device` 里有回退。

### 电平：为什么单独开 `/ws?levels=1`

电平 10Hz。一开始和字幕共用 `/ws`，后来意识到 OBS 的 CEF 被挂起时，
64 格队列 6 秒就会被电平塞满，真正要显示的字幕反而被丢掉。
现在 `Publisher` 按客户端记录是否订阅 level，字幕页不接收。设置页的 meter 只是画条，
不影响推理线程。

门限在 UI 上用 dBFS 显示（默认 0.008 ≈ -42 dBFS），因为「-42 dB」比「0.008」可读。
实际门限还会被噪声底抬高（`max(threshold, floor×noise_ratio)`），这点写进了设置页提示。

### 记录：连续 WAV + offset，而不是每句一个文件

只存每句话的 WAV 会丢掉句子之间的停顿，以后想复现分句/重跑 ASR 就没有上下文了。
所以存一条连续 WAV，`lines.jsonl` 里每句只记 `audio` + `start_s`/`end_s`：
既能直接听整段，也能按偏移切片。

- 写盘在 `record.py` 的独立线程，pipeline 线程只做 int16 转换 + 入队；
- `max_minutes` 默认 60，超过就分段（16k/16-bit 单声道约 115MB/小时）；
- 默认 `record.enabled = false`；设置页开关即时生效，不重启；
- 数据只在本机，不上传；`README.txt` 里写了「可能录到其他人声音，分享前确认同意」。

### 补充（同日）：自动打开设置页的时序修复

用户反馈"启动后浏览器没有打开设置页"。代码本身会开，但原来的判断有漏洞：
只做 TCP connect 就开浏览器。uvicorn 是**先绑定端口、再跑 lifespan**，这时候打开浏览器
会看到「このサイトにアクセスできません」，而浏览器不会自己重试，用户就以为没打开。

改成轮询 `/api/health`，拿到 200 才调浏览器；同时：

- 控制台明确打印「設定ページをブラウザで開きました：URL」或失败原因；
- Windows 下 `webbrowser.open` 返回 False 时再用 `os.startfile` 兜底；
- 等待上限从 15s 提到 30s，首次加载模型较慢的机器也够；
- 用 `BROWSER` 环境变量 + 一个只记录 URL 的 `.cmd` 做过端到端验证（不真的弹浏览器）。

另一个常见原因：**跑的是旧版 exe**。`dist\LiveSub-0.4.0\LiveSub.exe` 里没有这个功能；
新版是 `dist\LiveSub\LiveSub.exe`，启动横幅应显示 `LiveSub 0.5.0`。

## 2026-10-22：0.5.1（诊断版）——「电平在动，字幕不出」

### 报告与推断

主播反馈 0.5.0「音声の入力レベルは動くんだけど字幕動かない」，开发机完全正常。
对方发来的设置页截图里有三条关键信息：

- 电平 **-28 dB**，状态是「発話を検出」→ 音频已经进了 pipeline，VAD 也过了；
- 设备是 **In 1-2 (MOTU M Series) (2ch)**（2ch 音频接口）；
- 增益 **3.8×**、门限 **-65 dB**（调到底）——这是"以为声音小"的补救，不是原因。

VAD 之后只剩四步：切句 → ASR → composer → WS/OBS。0.5.0 没动切句，overlay 的 diff 也只有
自动清屏 3 处，所以最可疑的是 **ASR 返回空串**：`composer` 会静默丢掉，屏幕上什么都不会有，
`metrics` 里也看不出来。

再看实现：`MicSource` 写死 `indata[:, 0]`。2ch 接口把麦克风插在 **输入 2** 时，第 1 路只有串音：
电平会动、VAD 能触发、ASR 拿到的是噪声 → 空串 → 没有任何字幕。开发机是 1ch USB 麦，
所以永远复现不了。

### 做法：先让故障自己说话

没有直接改猜测，而是先把"信号链的每一段"变成可观测的：

1. `Pipeline` 增加计数：`frames` / `speech_frames` / `utterances` / `asr_calls` / **`asr_empty`** /
   `emitted`，外加 `last_frame_age_s`、`clients`（字幕页 / 设置页连接数）。
2. 保留最近 20 秒音频（`_recent`，约 1.2MB），诊断页可以拿它**重跑一次 ASR**：
   出字 = 音频/识别正常，问题在显示；不出字 = 音频侧问题。这一步把"猜"变成"测"。
3. 设置页新增「診断」tab：六段 ✓/!/✕ + 一行判定；`/api/diag`、`/api/diag/recent` 暴露同样的数据。
4. 「サポート用ファイルを保存」：`diag.json` + `summary.txt` + `config.toml` + 直近 10 秒 WAV +
   日志末尾打成一个 zip。**不自动上传**，用户自己决定发不发。
5. 顺手修根因：`audio.channel`（0 基，-1=全混）。`MicSource` 尽量按 2ch 打开（为了分通道电平），
   打不开自动退回 1ch；默认仍是 0，老配置行为不变。
6. `_diag_verdict` 把结论按信号链顺序写死（音声 → VAD → 切句 → 识别 → 字幕 → OBS），
   并在单测里固定分支，避免以后改文案改出误判。

### 经验

- **"电平在动"只能证明采集和 VAD，不能证明识别**。以后排障先问"诊断页的 asr_calls / asr_empty"。
- **空结果必须有计数**。没有计数的失败，在远程排障里等于不存在。
- **多通道设备是默认假设之外的世界**：单声道开发机上的"显然正确"，在 2ch 接口上就是静音。
